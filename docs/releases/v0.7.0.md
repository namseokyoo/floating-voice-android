# Floating Voice v0.7.0 — Multi-Destination Voice Routing

## Release-candidate contract

- Package: `com.sidequestlab.floatingvoice`
- Version: `0.7.0` (`versionCode 19` for RC2; RC1/versionCode 18 revoked)
- Android: 10+ (`minSdk 29`, `targetSdk 36`)
- ABI: `arm64-v8a` only
- APK signature schemes: v2 and v3
- Signing certificate SHA-256: `FD:97:82:9D:19:F8:B0:57:5B:79:EC:1E:8B:7A:26:16:A0:69:7C:EE:86:5D:29:B0:B5:28:78:3C:39:88:AB:A6`
- Distribution: official release-signed APK, GitHub Release only after final A52s acceptance

RC2 is the active acceptance candidate and is not yet the final GitHub Release. RC1 was revoked before device acceptance because a late catalog callback could rebuild an old-account route while logout was still closing. Its exact filename, byte size, SHA-256, certificate, and source commit are recorded after the commit-bound clean build.

## What changed

- Store and manage multiple verified Telegram private-bot destinations.
- Keep a persistent default destination and allow a current-recording override.
- Verify canonical bot, chat, and authenticated-account identities without sending a test message.
- Migrate the previous single destination as a blocked `NEEDS_REVERIFY` candidate until explicitly re-verified.
- Persist the destination catalog with versioned encrypted atomic storage and corruption recovery.
- Freeze account, destination, chat, bot identity, verification revision, and recording path before TDLib send.
- Retain failed or uncertain dispatch records and recording files; automatic retry and implicit fallback remain disabled.
- Reject stale account, lookup, picker, and send callbacks.
- Clear transient routing when the service or authenticated account changes.
- Recover from the authentication-code screen with a truthful resend countdown and an in-place phone-number correction path.

## Safety rules

- Only verified, enabled private bots belonging to the current authenticated account are selectable.
- Deleting or disabling a destination never rewrites an existing pending dispatch.
- A send uses only its immutable snapshot; changing the visible default cannot redirect it.
- `queued`, final success, failure, and uncertain delivery are separate states.
- The recording file is deleted only after final TDLib success has first been durably recorded.
- Setup, add, and re-verification flows send no automatic message.

## RC2 user-operated A52s matrix

Install over the existing release-signed app without uninstalling, then verify:

1. Telegram session and existing target survive the update.
2. A migrated target is blocked until explicit re-verification.
3. Add or re-verify two private bots; no test message is sent during verification.
4. Set a default target, record twice, and confirm both arrive only there.
5. During a recording select the other target, send once, then confirm the next recording returns to the default.
6. Cancel a recording after changing its target; confirm nothing is sent.
7. Disable or delete a non-default target and confirm no silent replacement or fallback occurs.
8. Change the default while another recording is active; confirm the active recording keeps its displayed target.
9. Turn off the network before stopping a recording; confirm failure/uncertain status retains the file and does not auto-retry.
10. Restart the app/service and confirm no transient current-recording selection survives.
11. Log out and confirm the floating service stops; log back in and confirm wrong-account destinations stay blocked.
12. At the Telegram code screen, confirm resend stays disabled during the countdown, becomes available when Telegram permits it, and phone-number correction requests a new code without trapping the UI.
13. Check normal and large font, both screen edges, picker Back/outside close, stop, cancel, and destination controls.

All phone installation and interaction are performed by the user. A build PASS is not a device PASS.

## Final release gate

Any source, resource, manifest, or build-setting change after RC2 delivery revokes RC2 and requires a new `versionCode`, a new signed candidate, full automated regression, and repeated A52s validation. The final release is either the exact accepted RC bytes or a rebuilt final APK that is installed and tested again before tagging and publication.
